# Vector Storage

## Overview

Document chunk embeddings are stored in PostgreSQL using the pgvector extension, accessed through Mastra's `PgVector` driver. All chunks are stored in a single index named `knowledge_base`.

## Index Structure

**Index name:** `knowledge_base`

Each vector entry consists of:

- A deterministic chunk ID (SHA-256 hash of `documentId:startIndex:textPrefix`)
- The embedding vector (dimension set by `EMBEDDING_DIMENSION`)
- A JSONB metadata object

## Chunk Metadata

Every chunk's metadata JSONB includes:

| Field           | Type           | Description                                                      |
| --------------- | -------------- | ---------------------------------------------------------------- |
| `text`          | string         | The full chunk text                                              |
| `documentId`    | string         | Parent document UUID                                             |
| `syncTargetId`  | string         | Sync target UUID                                                 |
| `source`        | string         | S3 object key                                                    |
| `title`         | string         | Document title (from LLM extraction or user-provided)            |
| `section`       | string         | Section heading (from HTML chunking, empty otherwise)            |
| `keywords`      | string         | Extracted keywords (comma-separated)                             |
| `startIndex`    | number or null | Byte offset of the chunk in the source text                      |
| _custom fields_ | varies         | Any custom metadata fields from the document's metadata template |
| `_searchMeta_A` | string         | Searchable custom metadata at critical weight (optional)         |
| `_searchMeta_B` | string         | Searchable custom metadata at high weight (optional)             |
| `_searchMeta_C` | string         | Searchable custom metadata at moderate weight (optional)         |
| `_searchMeta_D` | string         | Searchable custom metadata at standard weight (optional)         |

## Upsert

The upsert operation writes all chunks for a document in a single call:

```typescript
await vectorStore.upsert({
  indexName: 'knowledge_base',
  ids: chunkIds,
  vectors: embedded.map((e) => e.embedding),
  metadata: embedded.map((entry, i) => ({
    text: entry.text,
    documentId,
    syncTargetId,
    source: sourceKey,
    title: docTitle,
    section: entry.metadata?.section ?? '',
    keywords: entry.metadata?.excerptKeywords ?? '',
    startIndex: startIndices[i],
    ...mergedMetadata,
    ...searchMetaFields, // _searchMeta_{A,B,C,D} from buildSearchMetaFields()
  })),
});
```

## Chunk ID Generation

Chunk IDs are deterministic, generated by `makeChunkId()`:

```
SHA-256( documentId + ":" + startIndex + ":" + first200CharsOfText )
```

This means re-ingesting the same document with the same content produces the same chunk IDs, enabling true upsert semantics. If document content changes, new chunk IDs are generated and old ones are cleaned up by `deleteDocumentVectors()` before re-ingestion.

## Weighted tsvector (Full-Text Search)

Each chunk has a `content_tsvector` column computed by a PostgreSQL `BEFORE INSERT OR UPDATE` trigger. The trigger uses weighted tiers so title/section matches rank higher than body text matches:

| Tier | Weight | Content                                          |
| ---- | ------ | ------------------------------------------------ |
| A    | 1.0    | `title`, `_searchMeta_A` (critical custom)       |
| B    | 0.6    | `section`, `keywords`, `_searchMeta_B` (high)    |
| C    | 0.4    | `_searchMeta_C` (moderate custom — default tier) |
| D    | 0.2    | `text` (chunk body), `_searchMeta_D` (standard)  |

The `_searchMeta_*` fields are populated by `buildSearchMetaFields()` during ingestion. Only metadata fields explicitly marked as searchable (via `searchable: true` or `searchPriority` on the field definition) are included — this is opt-in per field.

Tier weights are configurable via `RAG_FTS_WEIGHT_{A,B,C,D}` env vars. The `ts_rank_cd()` call in `hybridQuery` passes these weights to PostgreSQL.

### Dirty Marking & Lightweight Refresh

When search settings (`searchable` / `searchPriority`) change on a field group or template, affected documents are marked `search_meta_dirty = true`. The sync flow detects these via `computeSyncDiff()` as `metaRefreshFiles` and runs a lightweight job (`metaRefreshOnly`) that recomputes `_searchMeta_*` fields via SQL -- no re-download, no re-embed. The `refreshDocumentSearchMeta()` pipeline function handles the SQL update. A direct API endpoint (`POST /v1/sync-targets/:id/refresh-search-index`) can also trigger this outside of sync.

## Chunk Retrieval

`getChunksByIds(chunkIds)` fetches full metadata for a list of chunk IDs from the vector store. This is used by:

- **Citation hydration** -- messages store minimal `_chunkSources` references (chunkId + displayIndex only); full metadata is hydrated on thread load
- **Scoring** -- retrieval quality scorers need the chunk text to evaluate relevance

## Update Operations

Three targeted update operations modify vector metadata without re-embedding:

### `updateDocumentVectorTitle`

Updates the `title` field in all chunks belonging to a document. Called when a user edits a document's title in the admin UI.

### `updateDocumentVectorSource`

Updates the `source` field in all chunks when an S3 object key changes (e.g., file rename).

### `updateDocumentVectorMetadata`

Merges custom metadata keys into existing chunk JSONB. Used when document metadata is edited without re-ingesting. This is a `||` (JSONB merge) operation, so existing keys not in the update are preserved.

## Deletion

`deleteDocumentVectors(vectorStore, documentId)` removes all vectors where `metadata->>'documentId'` matches. This is called:

- Before re-processing an updated file (to clear stale chunks)
- When processing a `delete-file` job (document removed from S3)
